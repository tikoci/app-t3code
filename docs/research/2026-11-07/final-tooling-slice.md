# Final agent-tooling slice (issue #5): evidence and remaining matrix

Habitat C (orca, amd64 Linux, Docker 29.9.2), 2026-11-07. Baseline: `main`
at `dfd14b5` (slice 5, #12, `labs` payload).

## What changed

- `browser` and `agents-extra` are no longer tool groups. The browser's
  native libraries stay in the image's first apt layer. T3's browser setup is
  unchanged, with no relocation, launch hook or patch. The libraries are now
  core library checks.
- **Muse is no longer bundled.** The Meta installer layer is gone. A
  user-installed `muse` (Meta's installer defaults to `$HOME/.local/bin` =
  `/data/.local/bin`) and Muse config, auth and history under `/data` are
  untouched. T3's Muse driver is untouched. Codex and opencode (npm globals)
  and the background Claude Code install are unchanged. Per-harness
  provisioning is #13.
- Default selection: `T3CODE_TOOL_GROUPS="capture labs vpn routing dev"` in
  the Dockerfile `ENV`, both YAML files and `DEFAULT_TOOL_GROUPS`. Unset or
  empty also selects it. `none` is core only, and `all` stays a convenience
  that also picks up future groups. The selector reports `defaulted`.
- Core bootstrap audit: `uv`/`uvx` 0.13.7 (from `ghcr.io/astral-sh/uv`,
  pinned `UV_VER`) with `UV_PYTHON_DOWNLOADS=manual`, plus the `sqlite3`
  CLI. Codex/opencode, uv/uvx, sqlite3, `fc-list` and the browser libraries
  became core checks. No other SDKs were added.

### Review follow-up: login-shell core readiness

In the initial full image (`c8e4732`), a **login shell** as `node` reported
`core: degraded (missing: ethtool)`, as on `main`. Debian's
`/etc/profile` drops `/usr/sbin` from a non-root PATH, and `ethtool` lives
there. The server environment (the image PATH) keeps `/usr/sbin`, so the
entrypoint, `docker exec` and the replacement test report `ready`. This
predates this slice. The review follow-up restores the system sbin paths in
`profile.sh`, after user-installed tools, and adds ordinary/login-shell core
readiness assertions to the replacement test. Offline Docker smoke checks
against the full image with the revised profile mounted verify both shells
report core `ready`; this profile follow-up does not itself claim another
full image build or replacement run.

## Recommended next run: full build plus a local CHR on the Mac

This is a handoff for the developer's Apple Silicon Mac (habitat B). Nothing
below has been run. It needs provider credentials and possibly a registry
push, which are the developer's decisions.
The `quickchr start`, `quickchr snapshot` and `centrs transfer` examples
were checked against the full image's offline CLI help; guest operations
in this procedure remain unexecuted.

**Prerequisites.**

- Docker Desktop or OrbStack with buildx, about 15 GB free for the image and
  build cache.
- Bun 1.4.x.
- `quickchr` and `centrs` on `@next`. Check with `quickchr doctor`: quickchr
  0.5.6 or later is needed for ARM64 firmware discovery.
- 30 GB or more free for CHR disks. The qcow2 files are sparse, but nested
  lab disks grow.
- A Claude login (subscription or `ANTHROPIC_API_KEY`) and a Codex login
  (ChatGPT or `OPENAI_API_KEY`). Model usage is subject to the chosen
  provider's plan and billing.

**Network.** The CHR pulls about 0.8 GB of image (compressed) and then
about 120 MiB of default payloads. A free CHR license caps upload at
1 Mbit/s per interface. An eligible `p1` trial raises that limit to 1 Gbit/s;
`--license-level p1` also needs a MikroTik account supplied through
quickchr's license options or environment. The procedure does not assume
that a trial is available or already activated.

**Speed.** On Apple Silicon, quickchr falls back to TCG for ARM64 CHRs
(tikoci/quickchr#97), and x86 CHRs are TCG too. Size waits for emulation:
boot and image unpack can take tens of minutes.

1. **Offline checks and a native ARM64 build.** On the PR branch, run:

   ```sh
   bun install && bun run check && bun run test
   docker buildx build --platform linux/arm64 --build-arg T3CODE_VER=0.1.6 \
     -t app-t3code:final-slice --load .
   ```

   Record the build time, the image size and the `deb-lock` lines (ARM64
   lock sizes).

2. **Native ARM64 replacement test.** Run
   `APP_T3CODE_DOCKER_IMAGE=app-t3code:final-slice bun test test/container-replacement.test.ts`
   with no `*_QEMU_USER` flags. This is the first native ARM64 host run of
   all five payloads, the unprivileged tool scripts (labs includes the QEMU
   firmware/PSCI smoke tests and `quickchr doctor` firmware discovery),
   offline relink, the image default and `none`. Then boot a real CHR from
   the labs payload inside that container:

   ```sh
   docker run -d --name labs-probe -v labs-probe:/data app-t3code:final-slice
   # wait for: docker exec labs-probe t3code-tools status  ->  labs ready
   docker exec labs-probe quickchr start --name inner --arch arm64 --accel tcg
   docker exec labs-probe centrs retrieve --quickchr inner /system/resource
   docker exec labs-probe quickchr snapshot inner save s1    # then list/load/delete
   docker exec labs-probe quickchr remove inner
   ```

   Also try a file transfer with `centrs transfer --quickchr inner …`, and the
   x86 guest. Docker Desktop has no `/dev/kvm`, so this is TCG too.

3. **Get the image to the CHR.** RouterOS pulls from a registry and cannot
   read the Mac's Docker store. Either:

   - (a) after merge, use the CI-published `ghcr.io/tikoci/app-t3code:0.1`.
     This matches production best.
   - (b) before merge, push a **non-production** tag (for example
     `ghcr.io/tikoci/app-t3code:pr-<n>`; never `:0.1`, `:0` or `:latest`)
     and install a throwaway copy of the YAML whose only change is `image:`.
     Do not dispatch `ci.yml` on the branch: it pushes the release tags.

4. **CHR with the app.** Follow the README's verified install flow. With
   quickchr, use `--device-mode-enable container`,
   `--add-package container`, `--boot-size 8G`, `--add-disk 24G`,
   `--mem 4096 --cpu 4` and a `--forward` for 3773, using ARM64 (and x86 if
   time allows). Then format the disk ext4, run `/app/settings/set disk=…`,
   `/app/add yaml=… use-https=no` and enable the app. Leave
   `T3CODE_TOOL_GROUPS` at the shipped default. Record the image pull and
   unpack time and the free space on the app disk.

5. **Readiness.** `/container/shell` into the app and run
   `t3code-tools status` until all five groups are `ready`; keep
   `/data/.local/share/t3code-tools/install.log`. Record the per-group
   install time over the CHR's link, the disk used, and that the web UI
   answered while the groups were still `pending`.

6. **Connect Claude and Codex through T3.**
   - Pair the browser with `t3-pairing-link` (README) through the forwarded
     port.
   - Claude: in a T3 terminal check `command -v claude` (the background
     install should have put it in `/data/.local/bin`; see
     `/tmp/install-claude-code.log`), then run `claude` and log in.
   - Codex: `codex login` (device or browser flow).
   - Alternatively, add `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` with the
     README's replace-one-key script pattern (spaces, never commas, and keep
     the other entries).
   - Start one small thread per provider in a project under `/data/projects`
     and confirm both run.

7. **Persistence and replacement.** With a project, threads, settings and
   both logins in place:
   - Use the replace-one-key script to set `capture labs`, check
     `:put [/app/get t3code environment]`, and check that the other keys
     survived.
   - Check that `vpn`, `routing` and `dev` are `not-selected` with their
     payloads kept, then set the default list back. Groups should relink
     with no download.
   - Run `/app/update`. If a second, rebuilt image is pushed to the test
     tag, this is a digest-changing replacement that has never been tested
     on RouterOS.
   - Reboot the CHR.
   - After each step, verify the T3 environment id, projects, threads,
     settings, `claude`/`codex` login state and the payload ids.
   - **Never** use `/app/set yaml=`: it wipes app volumes on 7.25.1 and
     7.26beta5.

8. **Nested labs on RouterOS (best effort).** Inside the app, start an inner
   CHR with `quickchr` (TCG in a container in a TCG CHR). Use a generous
   `--timeout-extra`, and record either success or the time to failure.
   Also try `centrs` reads, transfer, snapshot and cleanup.

9. **Optional (#7, not #5).** Try the 7.25 per-service privileged mode on a
   **separate** throwaway app and record the effective `CapEff`, `/dev/kvm`
   and `/dev/net/tun` inside it.
